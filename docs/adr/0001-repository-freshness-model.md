# 儲存庫新鮮度模型:陳舊上限,而非「盡快」

Vapor 對畫面新鮮度的承諾是**陳舊上限(Staleness Ceiling)**,不是「事件一到就刷新」:
檔案系統監看是**加速器**,讓外部變更在約 0.5 秒內反映;而心跳輪詢是**保證**,讓畫面
在任何情況下(包含監看無聲失效)都不會陳舊超過上限。監看正常時**仍然**保留低頻輪詢,
這是刻意的——監看的失敗模式是「靜悄悄地不再送事件」,而不是回報錯誤,只信任它等於
把正確性賭在一個不會叫的鬧鐘上。

## Considered Options

**閒置時零輪詢、零 Git 子行程**(R2 原始目標)。放棄了。它是一個可被觀測、可被行銷的
數字,但它換取的代價是「畫面可能無限期陳舊而使用者不會知道」。真正閒置時,30 秒一次
心跳的成本本來就接近零;真正忙碌時,省下的那點成本也無關緊要。

**只在監看失敗時才輪詢**(R2 已上線的作法)。放棄了。它只涵蓋「監看**建立**失敗」,
不涵蓋「監看建立成功但實際收不到事件」(網路磁碟、目錄被外部工具搬移)。後者才是會
讓使用者對工具失去信任的那一種。

## Consequences

- 合併(coalescing)必須有**最大等待上限**。只以「靜默後才送出」為條件會在持續 churn
  (`cargo build` 寫入 `target/`)期間**永遠不送出**——比輪詢更糟。上限把最壞情況從
  「完全不刷新」變成「以固定節奏刷新」。
- Vapor 的**讀取路徑必須對儲存庫零副作用**,否則刷新會觸發監看、監看再觸發刷新。
  `git status` 在工作區變動後會回寫 `.git/index`,因此唯讀指令一律帶
  `GIT_OPTIONAL_LOCKS=0`。代價是不保留 stat cache,大型儲存庫的 status 會略慢。
- Vapor **自己發起的寫入**造成的重複刷新(顯式刷新 + 監看再刷一次)刻意保留:
  pre-commit / post-commit hook 會在 commit 之後繼續改動工作區,顯式刷新看到的是
  hook 跑完**前**的狀態,監看那次才是最終狀態。
