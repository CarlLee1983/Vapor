# Vapor Open-Repository Design

**Goal:** Let users open a local Git repository in Vapor — both from the UI (an
"Open Repository" button) and from the terminal via a `vapor .` command that
behaves like `code .`.

**Status:** Approved 2026-06-08.

---

## Background

Vapor v1 shipped a complete Git workbench: the Rust backend reads repository
state, log, diff, and performs push; the React frontend renders all of it
through `useRepository`. But there is no way for a user to load a repository —
`loadRepository(path)` exists yet nothing in the UI ever calls it for the first
load. The app launches stuck on "No repository selected".

This design closes that gap with two entry points sharing one load path.

## Scope

In scope:

1. **UI entry** — an "Open Repository" button in the workspace toolbar that opens
   the native folder picker and loads the chosen directory.
2. **CLI entry** — `vapor .` (and `vapor <path>`) launches/focuses Vapor with that
   repository loaded, installed onto the user's PATH via an in-app
   `--install-cli` step. macOS only for now.

Out of scope (YAGNI, revisit later): recent-repositories list, manual
path-paste input, multiple windows, Windows/Linux CLI install.

## Architecture

The same frontend `loadRepository(path)` serves every entry point. New code only
*feeds paths into it* from three sources: the picker, a cold-start launch
argument, and a forwarded argument when the app is already running.

### Frontend

- **Toolbar button** (`src/App.tsx`): "Open Repository" calls
  `@tauri-apps/plugin-dialog` `open({ directory: true })`. A selected path goes
  straight to `loadRepository(path)`; cancel is a no-op.
- **Launch path on mount**: on first render, call a new `getLaunchPath()` wrapper
  (Tauri command `get_launch_path`). If it returns a path, `loadRepository(path)`.
- **Live forwarding**: subscribe to a Tauri `open-repo` event. When the
  single-instance plugin forwards a path from a second `vapor .` invocation, load
  it into the existing window.
- New wrapper file `src/lib/launch.ts` holds `getLaunchPath()` and the event
  subscription helper, keeping `App.tsx` thin and the Tauri surface mockable in
  tests.

### Backend (Rust)

- Add plugins: `tauri-plugin-dialog`, `tauri-plugin-single-instance` (desktop).
- New module `src-tauri/src/cli.rs`:
  - `parse_launch_path(args: &[String]) -> Option<PathBuf>` — pure: pull the repo
    path out of argv (first non-flag argument), ignoring the program name and any
    leading flags. Unit-tested.
  - `wrapper_script(app_binary: &Path) -> String` — pure: render the POSIX shell
    wrapper. Unit-tested.
  - `install_cli()` logic: write the wrapper to `/usr/local/bin/vapor`; if not
    writable, fall back to `~/.local/bin/vapor` and return a hint to add it to
    PATH.
- Startup: in `lib.rs`/`main.rs`, parse `std::env::args()` once, store the
  resulting `Option<PathBuf>` in Tauri managed state.
- New commands (`commands.rs`):
  - `get_launch_path() -> Option<String>` — returns the stored launch path
    (as a string) for the frontend to consume on mount.
  - `install_cli() -> Result<String, GitError>` — performs the install, returns a
    user-facing message (target path / PATH hint).
- single-instance callback: parse the forwarded argv with `parse_launch_path`,
  and if present `emit("open-repo", path)` to the frontend; focus the main window.

### Wrapper script

Generated by `--install-cli` after publishing (binary path resolved at install
time; `/Applications/Vapor.app/...` shown as the typical case):

```sh
#!/bin/sh
target="$(cd "${1:-.}" 2>/dev/null && pwd)" || {
  echo "vapor: directory not found: ${1:-.}" >&2
  exit 1
}
exec "/Applications/Vapor.app/Contents/MacOS/vapor" "$target"
```

The wrapper resolves `.` against the shell's working directory (the GUI app does
not inherit it) and execs the bundle binary directly so the single-instance
plugin can forward the argument to an already-running instance.

## Data flow

```
vapor .  ──► wrapper (realpath) ──► exec MacOS/vapor <abs-path>
                                          │
                  ┌───────────────────────┴───────────────────────┐
            app not running                                  app running
                  │                                                │
        startup parses argv                       single-instance callback parses argv
        → managed state                            → emit("open-repo", path) + focus
                  │                                                │
        frontend get_launch_path()                 frontend "open-repo" listener
                  └───────────────► loadRepository(path) ◄─────────┘
                                          ▲
                          toolbar "Open Repository" (folder picker)
```

## Error handling

- Non-Git directory (picked or passed): existing `GitError` flows through
  `loadRepository` to the existing toolbar error banner. No new UI.
- Wrapper given a missing directory: errors in the terminal, app not launched.
- `install_cli` without write permission: fall back to `~/.local/bin` and return
  a message telling the user to add it to PATH.

## Testing

- **Rust unit** (`cli.rs`):
  - `parse_launch_path`: program-name-only → `None`; `[prog, "/repo"]` → the path;
    leading flags skipped; empty → `None`.
  - `wrapper_script`: contains the resolved binary path and the `cd … && pwd`
    resolution line.
- **Frontend** (Vitest + Testing Library):
  - Clicking "Open Repository" with a mocked dialog returning a path calls
    `loadRepository` with it; a cancelled dialog does not.
  - On mount, a mocked `getLaunchPath` returning a path triggers
    `loadRepository`; returning `null` does not.
- **Manual**:
  - `npm run tauri dev -- -- /path/to/repo` → cold-start loads the repo.
  - With the app already open, run again → single-instance forwards and the open
    window loads the new repo.
